# 第15课：版本演进对比与功能扩展

> **目标**：通过对比项目几个关键历史版本，理解这个仿 OBS 桌面音视频项目是如何从“能录屏”逐步演进到“具备多线程、设备管理、图层系统、直播推流与调试体系”的，并在这个基础上学会从源码中提炼技术决策，理解为什么一个功能型项目最终会演变成一个架构型项目。  
> **对应文件**：`Tutorial/课程大纲.md`、`Tutorial/深度学习指南.md`、`RecorderConfig.h`、`EventBus.h`、`SystemController.cpp`、`FFmpegRecorder.cpp`、`mainwindow.cpp`，以及历史版本目录：`实现录屏/`、`实现音频设备发现/`、`解决混音问题/`、`重构采集逻辑，解决显示屏切换奔溃和安全桌面退出bug/`、`优化录制时间精确到秒/`、`实现EventBus和无边框风格，问题-直接运行会奔溃，调试能正常运行/`、`解决程序运行奔溃问题/`、`新添直播功能/`、`新增WGC采集，优化切换逻辑/`

---

## 1. 为什么第15课要专门讲“版本演进”

前14课基本都是围绕“当前版本源码”展开。

这种学习方式当然重要，因为你必须先能看懂现在的代码，才能真正理解项目在做什么。

但如果你只看最终版本，也很容易产生一个错觉：

- 好像这些架构天生就是这样设计的
- 好像 `EventBus`、多线程、直播推流、图层系统、本来就应该同时存在
- 好像当前这套代码结构是一次性想出来的

实际上，大多数真实项目都不是这样长出来的。

更常见的情况是：

- 先做出最小可用版本
- 遇到新需求，就补功能
- 遇到 bug，就改结构
- 遇到耦合和混乱，就重构架构
- 遇到性能与稳定性问题，就增加工程化手段

也就是说，**最终代码只是结果，版本演进才是过程。**

而第15课要做的，就是把这个过程重新找出来。

## 2. 为什么这个项目特别适合拿来做版本演进学习

在 `Tutorial/课程大纲.md:278` 之后，课程大纲已经明确把第15课定义为：

> **通过对比历史版本理解架构演进，完成综合实战。**

而在 `Tutorial/深度学习指南.md:165` 之后，又进一步强调：

- 这个项目保留了多个完整迭代版本目录
- 这些目录非常适合拿来做 diff 学习
- 对比相邻版本比只看最终代码更有价值

这意味着，这个仓库本身就不仅仅是“项目代码”，它还兼具了“成长记录”的作用。

对于学习者来说，这种材料很珍贵，因为你能看到：

- 某个功能最早是怎么被塞进去的
- 后来为什么发现这种写法不够用了
- 再后来为什么要重构
- 重构之后又引入了哪些新的复杂度

这和直接读一本已经整理好的教材不一样。

你看到的是：

> **一个真实桌面音视频项目，是如何一步一步从功能驱动，走向架构驱动，再走向工程驱动的。**

## 3. 用什么视角看这些版本，才不会只剩“文件变多了”

如果只是机械地比较目录差异，很容易陷入：

- 多了哪些文件
- 少了哪些函数
- 某几行代码怎么改了

但真正值得学的，不是“改了什么”，而是“为什么必须这样改”。

建议你用四个视角去读历史版本。

### 3.1 功能视角

看每个版本解决了什么用户需求。

例如：
- 最开始是录屏
- 后来加入音频
- 再后来支持直播
- 再后来支持图层和 UI 编辑

### 3.2 架构视角

看模块之间的关系有没有发生变化。

例如：
- 早期可能是直接调用
- 后来变成事件总线
- 再后来形成 UI / Controller / Backend 的分层

### 3.3 稳定性视角

看某次改动是不是为了修 bug、补生命周期管理、补异常处理、补线程协调。

例如：
- 显示器切换崩溃
- 程序运行崩溃
- 停止录制时资源释放问题

### 3.4 工程化视角

看项目是否越来越像“产品”，而不是“demo”。

例如：
- 日志系统
- crash dump
- 配置项不断增长
- UI 状态越来越完整
- 错误传播变得统一

所以第15课真正要训练的是一种能力：

> **你不只是会读代码，而是能从版本变化里看出项目为什么会变成今天这样。**

## 4. 第一阶段：`实现录屏/` 代表了什么

课程大纲把 `实现录屏/` 放在版本演进的起点，这非常合理。

因为一个仿 OBS 项目的最小可用闭环其实就是：

```text
采集画面
    ↓
编码
    ↓
写到文件
```

这个阶段的特点通常是：

- 目标明确：先把录制做出来
- 架构较简单：围绕单一主流程组织代码
- 复杂度集中在技术链路，不集中在 UI 和扩展性

这说明项目一开始最核心的挑战并不是“怎么做一个漂亮的软件”，而是：

> **怎么先把音视频采集与编码这条硬链路打通。**

从学习角度看，这个阶段最值得关注的是：

- 最小录制主链路长什么样
- 哪些模块是“项目成立的必要条件”
- 哪些复杂功能其实一开始都还不存在

也就是说，这一版更像“系统原型”。

它的价值不是架构完美，而是把最关键的技术风险先落地。

## 5. 第二阶段：`实现音频设备发现/` 为什么很关键

很多初学者会以为“给录屏加音频”只是再补一个输入源。

但实际上，只要加入音频设备发现，项目复杂度就已经明显上升了。

原因是视频和音频并不是同一种数据：

- 视频是帧
- 音频是连续 PCM chunk
- 视频更偏图像处理
- 音频更偏流式时钟与缓冲管理

而且音频一旦涉及设备发现，就说明程序开始要面对：

- 麦克风列表
- 系统回放设备列表
- 设备切换
- UI 选择项同步
- 配置保存与恢复

这意味着项目开始从“单一媒体链路”进入“多设备管理”。

这是一个很重要的转折点。

因为从这一步开始，系统不再只是处理数据，还要处理**设备状态**。

而一旦处理设备状态，后面就几乎一定会引出：

- 控制器逻辑
- 统一配置结构
- UI 与后台交互规范
- 错误处理与状态同步

所以你可以把这一版理解成：

> **项目第一次从纯采集录制工具，开始向完整桌面应用扩张。**

## 6. 第三阶段：`解决混音问题/` 暴露了什么本质难点

“解决混音问题”这个版本名本身就很有教学意义。

它说明项目不是简单地“添加音频”就结束了，而是在实际运行后发现：

- 多路音频不能直接拼起来
- 时间对齐有问题
- 音量叠加可能失真
- 编码端期待的格式与输入端不一致

这说明系统已经进入一个更真实的阶段：

> **最难的部分不再是“有没有这个功能”，而是“这个功能在真实时序下是否正确”。**

从当前 `FFmpegRecorder.cpp:98`-`118` 的 `applyFadeEffect()`、`FFmpegRecorder.cpp:190` 之后的音频编码流程也能看出，后来的实现已经明显不再是“收到音频就直接写出去”那么简单。

它开始处理：

- 多源音频缓存
- 重采样到统一格式
- FIFO 累积
- 按目标时间推进音频编码
- 混音后限幅
- 停止时淡出

这恰恰说明“解决混音问题”不是补丁式修修补补，而是一次对音频输出模型的升级。

所以这个版本告诉我们的经验是：

> **媒体项目里的很多技术债，不会在第一个版本爆出来，而会在你把第二路、第三路数据接进来之后才真正出现。**

## 7. 第四阶段：`重构采集逻辑，解决显示屏切换奔溃和安全桌面退出bug/` 为什么是架构信号

这类版本名特别真实。

它没有用“优化”“升级”这种抽象词，而是直接把问题写在目录名里：

- 显示屏切换崩溃
- 安全桌面退出 bug
- 采集逻辑重构

这往往意味着项目已经碰到了一个常见阶段：

- 旧逻辑在静态场景下还能跑
- 一旦遇到设备变化、系统状态变化、权限场景变化，就会暴露生命周期问题

例如：
- 当前采集对象还在使用旧显示器资源
- 切换时线程和对象销毁顺序不对
- 安全桌面切换导致 DXGI 采集中断
- 某些状态恢复流程不完整

这类问题的共同特点是：

- 不是单一 API 调错
- 不是单个 if 写错
- 而是对象生命周期与状态转换模型不够稳

所以当版本名里出现“重构采集逻辑”时，你就应该意识到：

> **项目开始从“功能扩展”进入“状态机与生命周期治理”。**

这通常是一个架构成熟的重要标志。

## 8. 第五阶段：`优化录制时间精确到秒/` 为什么说明项目开始关注“正确性”

时间精度问题在音视频项目里非常典型。

一开始很多程序都能录下来，但录出来并不等于录得准。

比如：
- UI 显示时间和实际文件时长不一致
- 视频帧率看起来正常，但音视频同步慢慢漂
- 停止时最后几秒被截断
- 计时使用系统时钟而不是媒体时间基，导致误差积累

而这个版本名说明，项目已经从“是否能录”进化到“录得是否准确”。

这背后反映的是两个层次的提升：

### 8.1 从功能完成，转向结果正确

用户视角下，能录是一回事；录制时长准确、同步稳定，是另一回事。

### 8.2 从界面时间，转向媒体时间

这类优化往往会逼着开发者重新理解：

- PTS / DTS
- time_base
- 帧推进与采样推进
- UI 定时器与真实媒体时钟的差别

所以这一版不是“小优化”，而是在补项目的时间语义。

这也是为什么第10课混流与时间戳同步会成为单独一课。

## 9. 第六阶段：`实现EventBus和无边框风格.../` 为什么是一次大重构

这是整个项目演进中非常关键的一步。

因为这里同时出现了两类变化：

1. `EventBus`
2. 无边框 UI 风格

表面上看，一个是架构，一个是界面，好像关系不大。

但放到真实项目里，它们往往会在同一个阶段一起出现。

原因是当软件开始更像“产品”时，会同时面对两种压力：

- 内部：模块越来越多，直接调用越来越乱，需要解耦
- 外部：界面越来越复杂，交互越来越多，需要更强的 UI 表达力

从当前 `EventBus.h:19`-`80` 可以看到，系统已经形成了比较清晰的信号分类：

- `cmd_`：View → Controller
- `data_`：底层数据流向 UI
- `state_`：状态变化与错误通知

这说明 `EventBus` 不只是“为了少传几个指针”，而是在给系统建立一种统一通信协议。

而从当前 `mainwindow.cpp:28`-`42` 的订阅列表也能看出，UI 层现在已经明显依赖这种总线式通信：

- 预览帧
- 图层更新
- 音频电平
- 录制状态
- 时长更新
- 设备列表
- 快照完成
- 错误提示
- 摄像头图层添加

这些都表明，到了这一阶段，项目已经不可能再维持“大家直接互相调用”的方式了。

所以这一版的真正意义是：

> **项目从“功能堆叠”转向“通信规则化”。**

## 10. 第七阶段：`解决程序运行奔溃问题/` 为什么说明稳定性开始成为主线

当一个版本目录直接叫“解决程序运行奔溃问题”，基本就说明开发重心已经变了。

前面的版本更多是在追求：

- 新功能
- 更完整的输入输出链路
- 更好的 UI 体验

而到了这里，重点变成：

- 为什么程序会崩
- 为什么调试时正常、直接运行就崩
- 为什么某些线程、某些 COM 初始化在不同启动路径下表现不同

这背后其实代表一个桌面 Windows 项目特别常见的难点：

- 调试环境与发布运行环境不完全一致
- WinRT / COM / 图形设备初始化对线程模型很敏感
- 某些 race condition 在断点下消失，在真实速度下暴露

也正因为如此，第14课才会专门引入：

- `Logger`
- `CrashHandler`
- 顶层 `try/catch`
- dump 文件

所以从课程编排角度看，第14课和这个历史版本是前后呼应的：

- 历史版本告诉你“为什么不得不开始关注稳定性”
- 第14课告诉你“稳定性工程在代码里怎么落地”

## 11. 第八阶段：`新添直播功能/` 为什么会把编码模块再推高一个层级

直播功能的加入，并不是“把文件输出换成网络输出”这么简单。

它真正改变的是：

- 输出不再只有一种目的地
- 编码后的包需要服务两个下游
- 网络失败成为新变量
- 推流初始化和本地文件初始化不再共享同一失败语义

从当前 `RecorderConfig.h` 可以看到，配置结构已经明显为“双输出”准备好了字段：

```cpp
bool enableFileRecord = true;
QString savePath = "";

bool enableStreaming = false;
QString rtmpUrl = "";
QString streamKey = "";
```

而从 `FFmpegRecorder.cpp:126`-`134` 也能看到，当前录制线程在启动时已经明确区分：

- 文件输出是否初始化成功
- 推流输出是否初始化成功
- 如果两路都失败才整体退出

```cpp
bool fileOk = true, streamOk = true;
if (m_config.enableFileRecord) {
    if (!initFileOutput()) { emit errorOccurred("File Output Init Failed"); fileOk = false; }
}
if (m_config.enableStreaming) {
    if (!initStreamOutput()) { emit errorOccurred("Streaming Init Failed"); streamOk = false; }
}

if (!fileOk && !streamOk) { closeResources(); return; }
```

这段代码特别有代表性，因为它说明系统已经不是“单出口程序”了。

而一旦进入多出口，很多原本简单的逻辑都会变复杂：

- 包写给谁
- 时间戳如何分别维护
- 某一路失败时是否影响另一路
- 停止顺序和刷尾顺序如何安排

所以直播功能的本质价值不是“多了 RTMP”，而是：

> **它迫使编码输出模块从单通道思维，升级成多目标输出架构。**

## 12. 第九阶段：`新增WGC采集，优化切换逻辑/` 说明项目进入技术选型升级阶段

当版本名里出现“新增 WGC 采集”时，说明项目已经不满足于只有一种视频采集方案。

这其实是一个很成熟的信号。

因为早期项目一般只会先把一种方案跑通。

而当项目继续演进后，你会逐渐意识到：

- DXGI 擅长整屏
- WGC 更适合现代窗口采集
- 两者能力边界不同
- 系统兼容性、权限要求、窗口行为都不同

也就是说，这一阶段已经不是“补功能”，而是在做**技术路线扩展**。

从架构角度看，这意味着项目逐渐接受一个现实：

> **真实产品往往需要多个技术方案并存，而不是寄希望于一个 API 解决所有场景。**

而版本名中的“优化切换逻辑”又再次提示我们：

- 新能力引入后，状态切换问题还要再处理一次
- 技术选型升级常常会带来新的生命周期复杂度

这就是为什么系统演进不是线性的。

每次加入更先进的方案，往往都要顺便把旧有的控制逻辑再升级一遍。

## 13. 如果把这些版本串起来，你会看到一条很清晰的成长路线

把课程大纲里列出的历史版本按能力演进串起来，大致可以看到这样一条路径：

```text
先打通录制主链路
    ↓
再补音频输入与设备管理
    ↓
再修正混音与同步正确性
    ↓
再处理采集切换与生命周期 bug
    ↓
再优化计时精度
    ↓
再做架构解耦和产品化 UI
    ↓
再补稳定性与崩溃治理
    ↓
再扩展直播输出
    ↓
再引入新的采集技术路线
```

这条路径特别像真实工程中的项目成长轨迹。

因为它不是按“教材目录”长出来的，而是按“问题压力”长出来的。

也就是说，每一次版本升级，背后其实都对应一种新的压力来源：

- 功能压力
- 正确性压力
- 架构压力
- 稳定性压力
- 扩展性压力

这也是第15课最重要的一个认识：

> **架构不是一开始设计出来的，而是在问题持续出现时被逼出来的。**

## 14. 从当前源码反看，项目已经具备了哪些“最终形态特征”

如果把目光再拉回当前版本，你会更容易看出这些历史演进最后沉淀成了什么。

### 14.1 配置结构已经明显产品化

`RecorderConfig.h` 里已经不只是分辨率和码率，而是包含：

- 视频编码参数
- 本地录制参数
- 直播参数
- 音频参数
- 淡入淡出参数
- 窗口能力参数

这说明配置已经从“录制参数”变成了“应用行为参数”。

### 14.2 控制器已经明显中心化

`SystemController.cpp:46` 开始的 `initialize()` 里，集中连接了大量 `EventBus` 命令：

- 切换源
- 添加摄像头
- 开始/停止录制
- 更新配置
- 刷新设备
- 截图
- 切换音频设备
- 图层几何变更
- 麦克风开关

这说明控制器已经承担起“系统编排中枢”的角色。

### 14.3 UI 已经明显不是简单预览窗口

`mainwindow.cpp:28`-`42` 订阅了大量状态与数据信号，这说明主窗口已经承担：

- 预览
- 图层编辑
- 设备面板
- 状态展示
- 错误展示
- 录制控制

它已经接近一个真正的桌面工具前端。

### 14.4 录制线程已经明显不是“收到帧就写文件”

`FFmpegRecorder.cpp` 现在要处理：

- 视频队列
- 音频队列
- 双输出
- 停止淡出
- 编码器 flush
- 不同输出上下文的尾部收束

这说明当前系统已经从“最小实现”发展成了“功能 + 状态 + 工程性”并重的版本。

## 15. 为什么说当前项目的最大收获，不只是功能多，而是“分层开始清楚了”

很多学习者在看版本演进时，最容易把注意力放在功能数量上。

比如：
- 现在能直播了
- 现在能加摄像头图层了
- 现在能切换音频设备了
- 现在 UI 更复杂了

这些当然都重要。

但从工程角度看，真正更值钱的变化其实是：

- UI 层越来越集中在 `mainwindow.cpp`
- 事件通信越来越集中在 `EventBus.h`
- 协调逻辑越来越集中在 `SystemController.cpp`
- 编码输出越来越集中在 `FFmpegRecorder.cpp`

也就是说，项目虽然变复杂了，但同时也在努力让复杂度各归其位。

这就是成熟项目和纯功能堆叠项目的区别：

> **复杂度不是消失了，而是被组织起来了。**

## 16. 第15课真正要学的，不是“版本故事”，而是“如何读演进”

### 16.1 先找最早的最小可用版本

通过这种方式，你就不会只看到“代码越来越多”，而能看到：

- 技术债是怎么出现的

## 17. 为什么课程大纲把“暂停/继续录制”放作综合实战

在 `Tutorial/课程大纲.md:298` 之后，课程大纲把“暂停/继续录制”定义为综合实战，并明确指出要改四个模块：

- `EventBus.h`
- `SystemController.cpp`
- `FFmpegRecorder.cpp`
- `mainwindow.cpp`

这其实是一个很聪明的选题。

因为它看起来只是“加个按钮”，但实际上会逼你重新理解当前架构的每一层职责。

### 17.1 在 `EventBus.h` 层

你需要决定：
- 是新增单独的 pause/resume 命令
- 还是扩展现有 recording 状态表达

这训练的是通信协议设计能力。

### 17.2 在 `SystemController.cpp` 层

你需要决定：
- 暂停是控制 `m_recorder` 还是控制 `m_capturer`
- 暂停时视频预览是否继续
- 暂停时计时器是否停止

这训练的是系统编排和状态机设计能力。

### 17.3 在 `FFmpegRecorder.cpp` 层

你需要决定：
- 暂停时是停止接收帧
- 还是继续接收但不写入
- 时间戳如何处理，才能避免恢复后文件时长跳跃
- 音频暂停后恢复，怎么避免时间轴错位

这训练的是媒体时间语义与编码逻辑能力。

### 17.4 在 `mainwindow.cpp` 层

你需要决定：
- 按钮文案如何变化
- UI 当前是“录制中 / 暂停中 / 空闲”哪种状态
- 时长显示是否冻结
- 用户是否需要明确的视觉反馈

这训练的是前端状态表达能力。

所以“暂停/继续录制”并不是一个小功能，而是一个横跨全系统的练习。

它非常适合作为收官实战，因为它会迫使你把前14课的知识重新串起来。

## 18. 如果真的去实现“暂停/继续录制”，最核心的难点是什么

很多人第一反应会是：

- 暂停时别写帧
- 恢复时继续写帧

但这只是表面。

真正的难点在于：

### 18.1 时间轴不能断裂

如果暂停 10 秒，恢复后直接继续按真实时间戳写，最终文件里会出现：
- 大段空白
- 时长跳变
- 音视频不同步

所以暂停不是“停止”，而是“冻结媒体时间推进”。

### 18.2 录制状态和预览状态要分离

用户往往希望：
- 预览继续动
- 录制暂时停止

这意味着采集链路和编码链路不能简单绑死在一起。

### 18.3 音频路径比视频更难处理

视频可以跳过某些帧，问题相对直观。

但音频是连续流：
- 暂停时 FIFO 怎么处理
- 恢复时从哪里接着算样本数
- 是否需要丢弃暂停期间音频
- 是否需要重新对齐编码参考时间

### 18.4 UI 状态必须可解释

如果按钮只写“暂停”，但用户看不出当前到底是暂停中还是录制中，体验会混乱。

所以这个综合实战表面是功能，实质上考的是：

> **你能不能在已有架构上新增一种中间状态，而不把现有流程搞乱。**

## 20. 从学习方法上，你应该怎么真正学完这15课

如果你只是顺着文档读一遍，收获会有限。

更高效的方式是：

### 20.1 当前版本与历史版本对照着读

建议以“当前版本 + 某个历史目录”成对阅读。

例如：
- 先看当前 `SystemController.cpp`
- 再看早期版本里对应逻辑
- 比较控制职责为什么变多

### 20.2 每次只关注一个演进问题

比如今天只追：
- 为什么要引入 `EventBus`

明天只追：
- 为什么录制线程要支持双输出

后天只追：
- 为什么调试体系必须补上

不要试图一次性把所有版本差异全记住。

### 20.3 把“变化原因”写出来

每看完一个版本，自己写一句总结：

- 这个版本主要解决了什么问题？
- 为什么旧结构不够用了？
- 新结构带来了什么新复杂度？

这样你学到的就不是代码细节，而是工程判断。

## 21. 从工程角度重新理解整个项目
