## 2. 为什么桌面音视频项目特别需要日志系统

这类项目比普通单线程小程序更依赖日志，原因至少有四个。

### 2.1 它有多个线程

当前项目里至少能看到：
- UI 线程
- 视频采集线程
- 录制编码线程
- 音频采集线程

多线程意味着问题经常不是“这一行代码写错了”，而是：
- 时序不对
- 某个信号没发到
- 某个对象已经销毁但另一个线程还在用
- 某条链路偶发失效

这类问题如果没有日志，你很难复盘。

### 2.2 它依赖很多外部系统

例如：
- DXGI / D3D11
- WinRT 摄像头
- WASAPI
- FFmpeg
- Windows 窗口系统

这些组件一旦失败，往往不会替你自动生成一份“人类可读”的问题说明。
你必须自己把初始化过程和关键状态记录下来。

### 2.3 它有大量异步行为

比如：
- 视频帧是异步来的
- 音频 chunk 是异步来的
- 摄像头层是异步加入的
- UI 和后台之间是通过信号/槽交互的

异步行为最大的特点是：

> **真正出问题的地方，和最终表现出问题的地方，经常不是同一个位置。**

所以你需要日志把整条链串起来。

### 2.4 它可能只在用户机器上崩

开发机上没问题，并不代表发布后没问题。

例如：
- 不同显卡驱动
- 不同显示器数量
- 不同音频设备
- 不同权限状态
- 不同网络环境

这时候，如果用户只告诉你“软件闪退了”，而程序又没有日志和 dump，基本等于没有线索。

## 3. 这个项目的调试体系分成哪几层

从源码看，这个项目的调试/稳定性体系大致可以分成四层：

1. **运行日志**：记录关键过程与线程行为  
2. **错误传播**：让后台错误能传到 UI  3. **顶层异常兜底**：主流程抛异常时至少能留下日志并提示用户  
4. **崩溃转储**：程序硬崩时生成 `.dmp` 文件

你可以把它理解成：

```text
平时靠日志
出错靠错误事件
异常靠 try/catch
崩溃靠 minidump
```

这四层叠在一起，才构成一个相对完整的排查体系。

## 4. `main.cpp` 为什么一上来先做这三件事

在 `main.cpp:9`-`20`：

```cpp
int main(int argc, char *argv[])
{
    // 1. 初始化崩溃捕获
    CrashHandler::init();

    // 2. 初始化日志
    Logger::instance().init("app_log.txt");
    LOG_INFO("Application Launching...");

    qRegisterMetaType<QList<int>>("QList<int>");
```

这几行非常值得单独看。

### 4.1 第一步先初始化崩溃捕获

原因很直接：
- 越早注册未处理异常过滤器越好
- 这样主程序后面的崩溃才更有机会被接住

换句话说，作者并没有等到 UI 创建完成、控制器初始化完成以后才去做 crash handling，
而是把它放在应用入口最前面。

这是一种很合理的防线顺序。

### 4.2 第二步初始化日志

因为从启动那一刻起，后面的每一步都可能失败：
- 控制器初始化
- 线程启动
- 设备枚举
- 窗口创建

所以日志必须尽量早可用。

### 4.3 第三步注册元类型

这一步表面上属于 Qt 元对象系统，但放在这里也体现了“调试友好性”。

因为如果跨线程 `invokeMethod` 用到了未注册的类型，运行时行为可能出问题，
而且错误未必很直观。

所以：

> **越靠近应用入口完成这些基础设施初始化，越容易让后续问题变得可观测。**

## 5. `Logger` 为什么设计成单例

在 `Logger.h:21`-`26`：

```cpp
class Logger {
public:
    static Logger& instance() {
        static Logger instance;
        return instance;
    }
```

### 5.1 单例的直接目的

日志系统需要在全局很多地方都能方便调用：
- `main.cpp`
- `SystemController.cpp`
- `CrashHandler.h`
- 其他线程对象

如果每个类都自己持有一个 logger：
- 初始化顺序更复杂
- 文件句柄管理更复杂
- 很容易出现多个地方重复打开同一个日志文件

所以单例是一个很自然的选择。

### 5.2 为什么这里比“工具类随便写写”更严肃

日志系统本质上属于基础设施。

它和普通业务类不同的地方在于：
- 几乎所有模块都依赖它
- 它必须尽量稳定
- 它本身不能轻易再引入复杂依赖

所以当前项目让 `Logger`：
- 自己管理文件
- 自己管理锁
- 自己负责输出格式

这是一种典型的轻量基础设施写法。

## 6. `Logger::init()` 为什么暴露了一个真实工程坑

在 `Logger.h:28`-`37`：

```cpp
void init(const QString& filename) {
    QMutexLocker locker(&m_mutex);
    m_file.setFileName(filename);
    if (m_file.open(QIODevice::WriteOnly | QIODevice::Append | QIODevice::Text)) {
        m_stream.setDevice(&m_file);
        log(LogLevel::INFO, "=== Session Started ===");
    }
}
```

### 6.1 这段代码表面上很普通

它做的是：
- 打开日志文件
- 把 `QTextStream` 绑定到文件
- 写一行 session start

### 6.2 但这里其实有一个锁重入问题

因为：
- `init()` 先拿了一次锁
- 然后内部调用 `log()`
- `log()` 里又要拿同一把锁

如果这里用的是普通 `QMutex`，同一线程再次加锁就会卡死。

### 6.3 作者是怎么修的

看 `Logger.h:91`-`93`：

```cpp
QRecursiveMutex m_mutex;
```

并且源码注释明确写出：
- 之前这里调用 `log()` 会导致死锁
- 现在改成 `QRecursiveMutex`

### 6.4 这个点为什么特别值得学

因为它不是“语法知识点”，而是非常典型的工程问题：

> **基础设施代码自己调用自己时，很容易出现重入与锁顺序问题。**

这也是为什么日志系统虽然看起来小，但并不等于可以随便写。

## 7. `Logger::log()` 到底记录了哪些关键信息

在 `Logger.h:43`-`78`：

```cpp
QString logLine = QString("%1 [%2] %3 [%4:%5] %6")
                      .arg(timeStr)
                      .arg((uint64_t)threadId)
                      .arg(levelStr)
                      .arg(func)
                      .arg(line)
                      .arg(message);
```

这行格式化字符串信息量很大。

### 7.1 时间戳

```cpp
QString timeStr = QDateTime::currentDateTime().toString("yyyy-MM-dd HH:mm:ss.zzz");
```

带毫秒级时间。

这很重要，因为很多媒体与线程问题都和时序有关。

### 7.2 线程 ID

```cpp
Qt::HANDLE threadId = QThread::currentThreadId();
```

这意味着你能从日志里区分：
- 是哪个线程打印的
- UI 线程和后台线程是否在按预期工作

对于多线程桌面程序，这个字段非常有价值。

### 7.3 级别

日志级别在 `Logger.h:13`-`19`：

```cpp
enum class LogLevel {
    INFO,
    WARNING,
    CRITICAL,
    DEBUG_TRACE
};
```

说明项目至少区分了：
- 普通信息
- 警告
- 严重错误
- 调试追踪

### 7.4 函数名和行号

通过宏：

```cpp
#define LOG_INFO(msg) Logger::instance().log(LogLevel::INFO, msg, __FILE__, __LINE__, __FUNCTION__)
```

最终日志里会带上：
- 当前函数
- 当前代码行号

所以它不是单纯打印一段字符串，而是：

> **尽量把“是谁、什么时候、在哪个线程、在哪个函数”一起记录下来。**

## 8. 为什么 `flush()` 对这个项目尤其重要

在 `Logger.h:69`-`73`：

```cpp
if (m_file.isOpen()) {
    m_stream << logLine << "\n";
    m_stream.flush(); // 立即刷新，防止崩溃时日志丢失
}
```

### 8.1 如果不立刻 flush 会怎样

如果只写入缓冲区，不立即刷盘：
- 程序正常退出时通常没问题
- 但程序崩溃时，缓冲区里的最后几条日志可能根本没落盘

而真正关键的信息，往往恰恰是崩溃前最后几条。

### 8.2 这里体现的取舍是什么

立即 flush 的代价是：
- I/O 更频繁
- 性能可能略差一些

但作者显然认为：
- 这是一个桌面录屏工具
- 调试与稳定性优先级很高
- 每条日志都尽量落盘更重要

所以当前选择更偏向“排障友好”。

## 9. 为什么 Debug 模式还要输出到控制台

在 `Logger.h:75`-`78`：

```cpp
#ifdef QT_DEBUG
    std::cout << logLine.toStdString() << std::endl;
#endif
```

### 9.1 这说明日志有两种消费方式

1. 文件日志：用于事后排查  
2. 控制台输出：用于开发时即时观察

### 9.2 为什么两者都需要

- 崩溃后留存能力差

所以当前项目在 Debug 模式下保留了双通道输出。

这是很实用的做法。

## 10. `CrashHandler` 是怎么接管未处理异常的

在 `CrashHandler.h:14`-`17`：

```cpp
static void init() {
    SetUnhandledExceptionFilter(UnhandledExceptionFilter);
}
```

### 10.1 这表示什么

它把 Windows 的顶层未处理异常过滤器设置成了自己的回调函数。

也就是说，当程序发生某些未捕获的严重异常时，系统会转到：

```cpp
UnhandledExceptionFilter(EXCEPTION_POINTERS* pExceptionInfo)
```

### 10.2 这解决的是什么问题

对于这类 C++/Qt/Win32 混合项目，仅靠普通 `try/catch` 并不能覆盖所有崩溃。

例如：
- 空指针访问
- 非法内存访问
- 某些底层 native 异常

这些问题往往不会优雅地抛成一个 `std::exception` 给你。

所以项目又加了一层 Windows 级别的 crash 捕获。

## 11. 为什么崩溃处理器要先记日志再写 dump

在 `CrashHandler.h:20`-`24`：

```cpp
static LONG WINAPI UnhandledExceptionFilter(EXCEPTION_POINTERS* pExceptionInfo) {
    LOG_ERROR("CRASH DETECTED! Generating MiniDump (Lightweight)...");
    QString fileName = QString("Crash_%1.dmp").arg(QDateTime::currentDateTime().toString("yyyyMMdd_HHmmss"));
```

### 11.1 先记日志的意义

即使后面 dump 写失败了，日志里至少还能留下：
- 程序确实进入了 crash handler
- 当时尝试生成了 dump

### 11.2 时间戳文件名的意义

```cpp
Crash_yyyyMMdd_HHmmss.dmp
```

这样做有两个好处：
- 多次崩溃不会互相覆盖
- 更容易和日志时间对应起来

这是一种非常实用的排障设计。

## 12. `MiniDumpWriteDump()` 为什么是调试现场的核心证据

在 `CrashHandler.h:48`-`56`：

```cpp
BOOL ret = MiniDumpWriteDump(
    GetCurrentProcess(),
    GetCurrentProcessId(),
    hFile,
    dumpType,
    &mdei,
    nullptr,
    nullptr
);
```

### 12.1 它做了什么

它会把当前进程的崩溃现场写成 `.dmp` 文件。

这个文件可以被调试器读取，用于分析：
- 崩在哪个线程
- 调用栈是什么
- 异常上下文是什么
- 某些关键内存状态

### 12.2 为什么这对用户机器崩溃特别重要

因为很多 bug：
- 在开发机复现不了
- 只在某些驱动/设备环境下出现

这时 minidump 往往是你最有价值的第一手证据。

它比“用户说点了就闪退”要有用得多。

## 13. 为什么这里特意强调是“Lightweight” dump

在 `CrashHandler.h:41`-`46`：

```cpp
MINIDUMP_TYPE dumpType = (MINIDUMP_TYPE)(
    MiniDumpNormal |
    MiniDumpWithHandleData |
    MiniDumpWithIndirectlyReferencedMemory
);
```

### 13.1 这不是最大最全的 dump

作者并没有选择“全内存转储”，而是选择了更轻量的类型组合。

### 13.2 这样做的好处

- 文件更小
- 生成更快
- 更适合普通桌面应用
- 崩溃时更不容易因为 dump 太重而进一步出问题

### 13.3 代价是什么

- 你拿到的信息没有 full dump 那么完整
- 某些复杂问题可能分析能力有限

### 13.4 当前项目的取舍

这说明作者更偏向：

> **先保证大多数崩溃都能低成本留下证据，而不是一开始就追求最重型的崩溃分析方案。**

这是很务实的工程选择。

## 14. 为什么 `main.cpp` 里还要再包一层 `try/catch`

在 `main.cpp:28`-`48`：

```cpp
try {
    LOG_INFO("Initializing SystemController...");
    SystemController controller;
    controller.initialize();

    LOG_INFO("Showing MainWindow...");
    MainWindow w;
    w.show();

    return a.exec();

} catch (const std::exception& e) {
    LOG_ERROR(QString("Unhandled C++ Exception: %1").arg(e.what()));
    QMessageBox::critical(nullptr, "Fatal Error", "An unexpected error occurred. Check log file.");
    return -1;
} catch (...) {
    LOG_ERROR("Unknown Exception caught in main loop.");
    QMessageBox::critical(nullptr, "Fatal Error", "Unknown crash occurred.");
    return -1;
}
```

### 14.1 这和 `CrashHandler` 不是重复吗

不是。

两者覆盖的范围不同：
- `CrashHandler`：偏向系统级未处理异常
- `try/catch`：偏向 C++ 异常路径

### 14.2 为什么两个都要有

因为真实项目里的失败方式不止一种：
- 有的是 C++ 显式抛异常
- 有的是 native 层直接崩
- 有的是第三方库内部抛出异常

所以作者采取了双保险：
- 能 catch 的尽量 catch
- catch 不到的崩溃交给系统级处理

这比只押宝一种机制稳得多。

## 16. `EventBus` 在调试体系里扮演什么角色

在 `EventBus.h:46`：

```cpp
void fireError(const QString& msg) { emit state_error(msg); }
```

### 16.1 这说明错误不是每个模块自己弹窗

项目里的后端模块并没有都直接操作 UI。

它们更常见的做法是：
- 把错误变成一个事件
- 发给 `EventBus`
- 再由 UI 决定怎么展示

### 16.2 这为什么重要

如果后台线程自己随意弹窗：
- 线程边界混乱
- UI 逻辑分散
- 错误展示方式不统一

而 `EventBus` 让错误路径变成：

```text
后台模块发现错误
    ↓
fireError(...)
    ↓
UI 统一订阅并处理
```

这是一种很清晰的架构分层。

## 18. 后台线程初始化失败是怎么传给 UI 的

在 `SystemController.cpp:107`-`115`：

```cpp
connect(m_videoThread, &QThread::started, m_capturer, [this]() {
    HRESULT hr = RoInitialize(RO_INIT_MULTITHREADED);
    if (FAILED(hr))
        CoInitializeEx(nullptr, COINIT_MULTITHREADED);
    if (m_capturer->init()) {
        m_capturer->startCapture();
    } else {
        EventBus::instance()->fireError("Failed to initialize DXGI Capturer");
    }
});
```

### 18.1 这里体现了什么错误处理思路

启动视频线程后，不是假设采集器一定能初始化成功，
而是显式判断：
- 成功就开始采集
- 失败就发错误事件

### 18.2 为什么这比直接 `qDebug()` 一句更好

因为 `qDebug()` 只是给开发者看，
而 `fireError()` 可以把问题继续传给 UI 层。

这说明项目已经在区分：
- 调试输出
- 用户可见错误

这两者不是同一个层次。

## 19. `mainwindow.cpp` 如何成为错误展示的统一入口

在 `mainwindow.cpp:28`-`42`：

```cpp
EventBus *bus = EventBus::instance();
...
connect(bus, &EventBus::state_error, this, &MainWindow::onError);
```

### 19.1 这说明什么

说明 UI 已经订阅了全局错误事件。

也就是说，无论错误来自：
- 采集模块
- 控制器
- 编码器
- 其他后端路径

最终都可以汇聚到主窗口的统一处理函数。

### 19.2 这种设计的好处

- 错误展示样式统一
- 不用每个后端类都知道 UI 细节
- 后续如果想把错误改成状态栏提示 / toast / 日志面板，只改 UI 一处就够了

这也是典型的“业务与表现分离”。

## 20. `FFmpegRecorder` 里的 `printError()` 为什么很关键

在 `FFmpegRecorder.cpp:7`-`11`：

```cpp
static void printError(const QString& tag, int errCode) {
    char errBuf[AV_ERROR_MAX_STRING_SIZE] = {0};
    av_strerror(errCode, errBuf, AV_ERROR_MAX_STRING_SIZE);
    qCritical() << "[FFmpegError]" << tag << ":" << errBuf << "(Code:" << errCode << ")";
}
```

### 20.1 为什么不直接打印错误码

因为 FFmpeg 的很多错误码是整数，直接看数字几乎没有直觉意义。

### 20.2 `av_strerror()` 的价值

它把错误码翻译成更可读的文本。

于是开发者看到的不是：
- `-22`

而更接近：
- 参数非法
- 打开失败
- 连接失败
- 写 header 失败

这种“把底层错误翻译成人类语言”的动作，对调试效率非常重要。

## 21. 为什么 `FFmpegRecorder::run()` 里的失败处理很像状态机

在 `FFmpegRecorder.cpp:120`-`134`：

```cpp
if (!initVideoEncoder()) { emit errorOccurred("Video Encoder Init Failed"); closeResources(); return; }
if (!initAudioEncoder()) { emit errorOccurred("Audio Encoder Init Failed"); closeResources(); return; }

bool fileOk = true, streamOk = true;
if (m_config.enableFileRecord) {
    if (!initFileOutput()) { emit errorOccurred("File Output Init Failed"); fileOk = false; }
}
if (m_config.enableStreaming) {
    if (!initStreamOutput()) { emit errorOccurred("Streaming Init Failed"); streamOk = false; }
}

if (!fileOk && !streamOk) { closeResources(); return; }
```

### 21.1 这不是简单“报错然后退出”

这里区分了：
- 编码器初始化失败
- 文件输出失败
- 直播输出失败
- 两路都失败

### 21.2 这种分层报错有什么好处

它让你更容易从日志和错误提示里判断：
- 是编码器根本没起来
- 还是文件路径不行
- 还是直播初始化不行
- 还是双路都没法用

这说明调试友好不只是“有没有日志”，还包括：

> **错误是不是被拆成了足够清晰的阶段。**

## 22. 为什么线程相关日志在这个项目里很有价值

在 `Logger.h:55`：

```cpp
Qt::HANDLE threadId = QThread::currentThreadId();
```

再结合 `SystemController.cpp` 和 `FFmpegRecorder.cpp`，你会发现项目里很多关键模块都在不同线程运行。

### 22.1 线程 ID 能帮你看什么

例如：
- 某条日志是不是 UI 线程打出来的
- 录制线程是否真的启动了
- 某个错误是不是来自采集线程
- 某个操作是否跨线程执行了

### 22.2 为什么这在 Qt 项目里特别重要

因为 Qt 里很多 bug 都和线程亲和性、队列连接、对象所属线程有关。

如果日志没有线程 ID，你只能看到“出错了”；
有了线程 ID，你才能继续分析“是谁出的错”。

## 23. `DxGiCapturer::startCapture()` 的 `try/catch` 暴露了什么调试取舍

在 `DxGiCapturer.cpp:638` 开始：

```cpp
try {
    while (m_running) {
        QCoreApplication::processEvents();
        ...
    }
} catch (...) {
}
emit captureStopped();
```

### 23.1 这段代码想解决什么

它显然是在防止采集线程因为某个未预期异常直接炸掉整个流程。

也就是说，作者的意图可能是：
- 先把线程守住
- 至少保证程序别因为这里直接整段崩掉

### 23.2 但这里有什么问题

`catch (...) {}` 是空的。

这意味着：
- 异常被吞掉了
- 没有日志
- 没有错误上报
- 没有上下文信息

于是你最后只能看到：
- 采集停了
- 但为什么停，日志里没有

### 23.3 为什么这是本课最值得反思的点之一

这说明调试系统不是“有了 crash handler 就结束”。

如果中间某些线程把异常悄悄吞掉，
那你仍然可能遇到：
- 程序没崩
- 但功能失效
- 而且几乎没有线索

这是典型的“稳定性保护”和“可诊断性”之间的冲突。

## 24. 为什么说这个项目的调试体系已经有雏形，但还不算完全体

从源码看，它已经具备不少优点：

### 24.1 已有的优点

- 有统一日志系统
- 日志带时间、线程、级别、函数、行号
- 日志立即 flush
- 有顶层异常兜底
- 有 Windows crash dump
- 有 `EventBus` 错误传播
- 有一些启动/销毁阶段过程日志
- FFmpeg 错误能转成人类可读文本

### 24.2 仍然存在的局限

- 有些地方仍在用 `qDebug/qWarning/qCritical`，和 `Logger` 还未完全统一
- 某些线程异常可能被 silent catch 吞掉
- 错误事件和日志事件还不是完全统一的一套体系
- 当前没有看到专门的日志查看 UI
- 当前没有更细粒度的错误码分级或错误上下文对象

### 24.3 这说明什么

说明项目已经开始从“能跑”走向“可维护”，但还没有走到完整产品级可观测性。

不过对一个学习型开源项目来说，这种状态其实很有价值，
因为你能清楚看到：
- 哪些地方已经做了工程增强
- 哪些地方仍然留着继续演进的空间

## 25. 从工程角度重新理解第14课

这一课最重要的，不是记住几个 API 名字，而是理解这件事：

> **调试体系不是某一个类，而是一整条“信息留下来”的链路。**

在这个项目里，这条链路大致是：
- `Logger` 负责日常过程记录
- `CrashHandler` 负责硬崩时留下 dump
- `main.cpp` 负责应用级入口兜底
- `EventBus` 负责把后台错误送到 UI
- `SystemController`、`FFmpegRecorder` 等模块负责在关键阶段显式发出错误或状态信息

所以真正的核心不是“会不会调用 `MiniDumpWriteDump`”，而是：

> **当程序出问题时，开发者能不能从日志、错误事件、异常提示、dump 文件中把现场尽量还原出来。**

这才是桌面工具项目里“稳定性工程”的开始。
